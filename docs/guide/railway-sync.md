# Host the private sync service on Railway

Railway is one hosted option for the provider-independent service. Its [Hobby plan](https://docs.railway.com/pricing) currently has a $5/month minimum that counts toward resource usage; usage above that is billed separately. Review its pricing before creating a paid project.

The steps below deploy **one** service instance. [Railway starts with one replica by default](https://docs.railway.com/overview/advanced-concepts); to verify, open the service's **Settings → Scale → Regions** and confirm the count is `1` in one region. The snapshot writer serializes changes within that process, so do not scale it to multiple replicas against one volume. Keep changes staged until the source, volume, variables, and domain are configured, then deploy them together.

1. Create a Railway project and connect this repository as one service. In the service's **Settings → Source**, set **Branch connected to production** to `codex/v2.2`; connecting the repository alone may leave it on `main`, where the sync Dockerfile does not exist. Set `RAILWAY_DOCKERFILE_PATH=sync-server/Dockerfile` in its variables and keep the repository root as the build context. Railway documents [custom Dockerfile paths](https://docs.railway.com/builds/dockerfiles).
2. Attach one [persistent volume](https://docs.railway.com/volumes) mounted at `/data`. The image starts as root only to set the mounted directory's ownership, then runs the Node process as `node`. Keep one replica.
3. Add service variables: `PT_SYNC_TOKEN` (a freshly generated 64-character hex token from `openssl rand -hex 32`) and `PT_ALLOWED_ORIGINS` (the final HTTPS app origin plus `tauri://localhost,http://tauri.localhost,https://tauri.localhost`). Railway supplies `PORT` at runtime, and the service listens on that value. The image already sets `PT_SYNC_DATA_DIR=/data`, `PT_STATIC_DIR=/app/dist-private`, and `PT_SYNC_HOST=0.0.0.0`. Keep the token out of the repository and frontend build variables. [Railway variables](https://docs.railway.com/variables).
4. Generate a Railway domain under Public Networking. If asked for a target port before the first deploy, enter `8787` provisionally; after deployment, check the **Deploy Logs** for `Personal Treasury sync listening on 0.0.0.0:<port>` and edit the domain's target port to that actual value. Railway provides HTTPS automatically. Add the exact `https://…` origin to `PT_ALLOWED_ORIGINS` and set the service health check path to `/healthz`. Review all staged changes, then click **Deploy**. Confirm `https://…/healthz` returns `{"status":"ok"}` before uploading data. [Railway public networking](https://docs.railway.com/networking/public-networking).
5. Protect the volume separately from app version history. Railway's current Backups tab requires a Pro plan to create scheduled volume backups. If your plan supports them, schedule [daily volume backups](https://docs.railway.com/volumes/backups). On Hobby, export complete JSON backups from the app after major changes and periodically thereafter, and store them in encrypted storage outside Railway. App version history protects against a mistaken edit but cannot recover a lost volume.
6. If your existing treasury data is in the Mac app, connect it first under **Settings → Cloud sync** using the HTTPS URL, token, and a new sync passphrase. Repeat the passphrase for the first upload and wait for **Up to date**. Then open the HTTPS URL on the phone and connect with the same token and passphrase. Wait for **Up to date** before editing on either device.

No private financial data needs to be pushed to GitHub or placed in Railway variables. The server stores client-encrypted snapshots on the volume. Moving to another host means copying the data directory, updating the app URL, and resolving the first connection choice if the new URL has no remembered local baseline.
